# ETF 一级市场监控：Evolution / Decision Log

> 目的：保存“为什么系统最后变成现在这样”。
>
> 这份文件不保存逐行开发流水，也不复制聊天全文。只记录会改变认知、规则、数据口径或架构的关键节点，并保留错误、舍弃路径和未决问题。
>
> 项目知识沉淀统一采用三层结构：
>
> 1. **Canonical / Current**：当前有效认识与当前系统边界；
> 2. **Evolution / Decision Log**：认识与架构如何演化到当前状态；
> 3. **Runtime History**：真实市场运行中发生过什么、系统捕捉到什么。

## 记录规则

只有出现实质变化时才新增条目。优先记录下面七项：

1. **触发 / 问题**：什么现实问题触发了这次变化。
2. **旧认识 / 原方案**：变化前我们怎么理解、原本准备怎么做。
3. **证据 / 实测**：交易所数据、真实 ETF、运行结果、失败现象或案例。
4. **舍弃路径**：哪些方案被证明不合适，以及为什么不再采用。
5. **新认识 / 决策**：本轮之后当前采用什么认识或架构。
6. **未决问题**：仍然不知道什么，后面需要怎样验证。
7. **追溯**：关联代码、commit、数据快照或其他可复核来源。

原则：

- 不追求记录所有开发动作，只保留以后重新理解系统时仍然有价值的节点；
- 失败和错误必须保留，不能只留下最后正确答案；
- Canonical 只表达“现在是什么”，历史争论和旧方案放在这里；
- Runtime History 只记录真实运行事实，不把研究推断伪装成运行结果。

## 2026-10-06｜知识沉淀结构正式统一为三层

### 触发 / 问题

开发 ETF 一级市场监控时，发现代码 commit 能记录“改了什么”，但不能稳定保存“为什么这样改”；同时此前套利情报雷达已经形成较成熟的 Evolution / Decision Log 思路。

### 旧认识 / 原方案

ETF 项目最初只有一份 `DEVELOPMENT_LOG.md`，定位为“开发与认知日志”，已经会记录问题、判断、实测、修正和未决事项，但尚未与“当前有效认识”和“真实运行历史”明确分层。

### 证据 / 实测

本项目启动第一天已经出现多次值得长期保留的认知变化：

- 分类从单棵树改为“地区 × 资产 × 策略方式”的多维结构；
- 商品关键词曾把有色金属股票 ETF 误归为商品 ETF；
- 上交所真实 PCF 字段名与历史样例存在差异；
- 上交所 universe 子类比早期样例更复杂；
- 服务器无法直连深交所，促使项目复用已验证的官方 relay 架构。

这些内容如果只存在 commit 或聊天中，未来很难恢复完整的推理和取舍过程。

### 舍弃路径

- 不把聊天记录本身当项目知识库；
- 不要求每个 commit 都写成长篇解释；
- 不把所有研究、决策、运行事件塞进一个不断膨胀的日志文件；
- 不覆盖旧判断，只在 Canonical 中更新当前结论，在 Evolution Log 中保留演化路径。

### 新认识 / 决策

ETF 一级市场项目正式采用统一三层知识结构：

- `CURRENT.md`：当前有效边界、数据源、分类、监控原则和当前阶段；
- `DEVELOPMENT_LOG.md`：Evolution / Decision Log；
- `runtime_history/`：后续保存真实运行事件与阶段性统计的结构说明和历史文件。

该结构以后应优先复用于同类长期研究 / 运行项目，而不是每个项目重新发明一套日志方式。

### 未决问题

- Runtime History 最终按“每日事件文件”还是“事件流 + 周期汇总”保存，要等第一批真实监控事件出现后再决定；
- 哪些开发节点值得升级为跨项目通用原则，暂不提前抽象，先让 ETF 项目真实运行后再归纳。

### 追溯

- 分支：`feat/etf-primary-monitor-v0`
- 当前日志：`runtime/etf_primary/DEVELOPMENT_LOG.md`
- 当前状态：`runtime/etf_primary/CURRENT.md`
- 运行历史说明：`runtime/etf_primary/runtime_history/README.md`

## 2026-10-06｜V0 起点：先把一级市场地基做干净

### 触发 / 问题

目标不是先做一个“ETF 套利页面”，而是先获得一个可信的一级市场监控底座：

**全市场 ETF → 分类 → 官方申购赎回清单（PCF）→ 申赎容量 / 单账户容量 → 日变化事件。**

经济性、实时溢价、成交承接暂时不混入这一层。

### 旧认识 / 原方案

最初讨论时，分类倾向写成“境内 / 跨境 → 指数 / 商品 / 债券”等树状层级，并准备直接从交易所找到 ETF 后接申赎页面。

### 证据 / 实测

#### 1. 上交所 ETF 列表可作为正式 universe

实测官方 `FUND_LIST` 接口可以按 ETF 子类获取列表；不能只取一个分类或第一页。

已确认至少包括：

- 股票类
- 债券类
- 货币类
- 商品类
- 跨境类
- 科创 / 双创等交易所子类

其中部分大类单一子类已经超过 500 只，因此 universe 抓取必须显式处理分页和多子类并集。

#### 2. 513100 的上交所 PCF 可以直接读取一级市场容量

真实接口返回包括：

- 交易日
- 最小申赎单位
- 最小申赎单位净值
- 累计申购上限
- 单账户累计申购上限
- 净申购 / 净赎回上限
- 申购赎回开关
- 申赎机制

2026-09-30 的 513100 样本中，可直接派生出“总篮子数”和“单账户篮子数”，证明我们不需要靠名称或第三方页面猜测申购容量。

#### 3. 深交所官方源存在服务器网络可达性问题

当前服务器直连 `www.szse.cn` 出现 `Network is unreachable`。这属于访问线路问题，不是数据模型问题。

现有 LOF 系统已经有“GitHub Actions 获取深交所官方数据 → 服务器读取 last-good relay”的成熟模式，因此 ETF 项目优先复用这一基础设施，而不是引入第三方替代源。

### 舍弃路径

- 舍弃把“境内 / 跨境、股票 / 债券 / 商品、指数 / 主动”硬塞进单棵分类树的做法；
- 舍弃以名称关键词作为主要分类依据；
- 舍弃服务器直连深交所失败后改用第三方替代源的捷径；
- 第一阶段不加入溢价、成交承接和经济性，以免事实层和策略层耦合。

### 新认识 / 决策

1. **官方源优先**：SSE / SZSE 为 canonical。
2. **分类多维存储**：地区、资产、策略方式分开。
3. **PCF 先做摘要层**：先抓申赎状态和容量，不急于保存全量篮子历史。
4. **变化优先于状态**：日快照用于做 diff，事件才是监控输出。
5. **经济性后置**：先把一级市场事实做可信，再接溢价、成交、到账时间、券商可执行性。
6. **失败不隐藏**：网络不可达、字段变化、分类歧义都要进入日志，而不是只留下最终成功结果。

### 未决问题

- 跑出完整 SSE + SZSE ETF universe，并对分类分布做第一次审计；
- 为深交所建立 ETF 官方数据 relay，沿用 LOF 已验证的 last-good 机制；
- 全量接 PCF 摘要，形成每只 ETF 的“可申购 / 最小篮子 / 总容量 / 单账户容量”；
- 建立轻量日快照，开始产生第一批真实变化事件。

### 追溯

- 分支：`feat/etf-primary-monitor-v0`
- 核心目录：`runtime/etf_primary/`

## 2026-10-06｜全市场 PCF 从“能抓”修到可审计 relay

### 触发 / 问题

SSE 批量 PCF 可以稳定获取，但 SZSE 若在同一 runner 对数百只 ETF 逐个请求 XML，会出现大量 `403 Forbidden`。单纯增加重试不仅不能解决问题，还会继续触发 CDN / WAF 限制。

### 旧认识 / 原方案

早期方案是：从 ETF universe 推导代码，再按照两种常见文件名逐只尝试下载；只要整体覆盖率超过一个较低门槛即可进入 merge。

这个方案有两个问题：

1. 猜文件名会制造不必要请求；
2. “97% 覆盖就算通过”适合临时数据抓取，不适合用来生成市场变化事件——少掉的那部分可能恰好就是重要事件。

### 证据 / 实测

最终实跑确认：

- 全市场 ETF universe：1693，只数为 SSE 944 + SZSE 749；
- SSE PCF：944 / 944 找到；
- SZSE PCF：749 / 749 最终找到；
- 总 PCF：1693 / 1693；
- SZSE 12 shard 架构下，偶尔仍会出现单点 403，但 merge 阶段从新 runner 对极少缺口做受限恢复后可以补齐；
- 最新实跑曾有 1 个 SZSE shard 单点失败，被 sparse recovery 恢复；
- 另有 1 只 SSE PCF 的交易日落后于目标交易日，因此应标记 `stale`，而不是算作 `missing` 或静默替换。

### 舍弃路径

- 不再把“对每个代码猜两个文件名”作为主要下载机制；
- 403 后不继续在同一个 host 上盲目尝试更多候选文件名；
- 不接受“高覆盖率但不知道缺谁、为什么缺”的模糊成功；
- merge 不做第二次全市场抓取，只允许对极少数缺口做有上限的 sparse recovery。

### 新认识 / 决策

正式采用：

**官方当日 PCF 索引 → 12 shard 分散请求 → merge 完整性校验 → 极少缺口受限恢复 → last-good relay。**

同时把数据质量拆成两层：

- `missing`：没有拿到 PCF；
- `stale`：拿到了 PCF，但交易日不是目标交易日。

这使“文件覆盖率”和“当日有效率”不再混在一起。

### 未决问题

- 当前那 1 只 stale ETF 需要在后续审计中确认它是正常的官方历史文件状态，还是某一特殊产品类型的发布时间差异；
- 长期观察 WAF 失败率，若 sparse recovery 经常超过极少数，就应重新调整 shard 数 / runner 并发，而不是扩大重试上限。

### 追溯

- relay 分支：`etf-primary-data-relay`
- relay version：`etf-primary-official-relay-v2`
- 关键模块：`relay_prepare.py`、`pcf_shard.py`、`relay_merge.py`、`szse_relay.py`
- 工作流：`.github/workflows/etf-primary-szse-relay.yml`

## 2026-10-06｜Runtime History 首次真实落盘，并解决休市日重复写入

### 触发 / 问题

relay 已经能每天生成全市场 PCF，但如果每次运行都覆盖同一个交易日的 gzip / `current.json` / `last_run.json`，国庆等长休市期会产生一串“市场事实完全没变”的 commit。gzip 自带写入时间也会让文件字节变化，进一步放大无意义历史。

### 旧认识 / 原方案

最初 `runtime_cycle.py` 对同一交易日统一视为 `SAME_TRADE_DATE_REFRESHED`：不制造市场事件，但仍重写快照和运行摘要。

这在逻辑上避免了假事件，却没有做到存储层真正幂等。

### 证据 / 实测

2026-10-06 完成真实工作流：

- relay merge 成功；
- 新建独立运行数据分支 `etf-primary-runtime-data`；
- 第一份 baseline 成功写入，交易日 `20260930`；
- baseline PCF 1693 / 1693，stale 1，missing 0，event 0；
- `current.json`、`last_run.json`、`snapshots/20260930.json.gz` 均已实际存在；
- 新的幂等测试确认：同交易日且 `snapshot_sha256` 完全一致时，不重写三个文件；同交易日但事实摘要变化时，允许更新快照但仍不产生跨日事件。

### 舍弃路径

- 不把每次 workflow 运行都变成一条 Runtime History；
- 不用“最后抓取时间变化”制造数据 commit；
- 不把 Runtime History 和代码分支、relay 分支混在一起；
- 暂不把这套事实层直接部署到现网服务器，先让 GitHub Actions + 独立数据分支形成可复核闭环。

### 新认识 / 决策

当前持久化分三条线：

1. **代码 / 规则**：`feat/etf-primary-monitor-v0`；
2. **最新官方数据 relay**：`etf-primary-data-relay`；
3. **跨日运行历史**：`etf-primary-runtime-data`。

Runtime 规则：

- 首次只建 baseline；
- 新交易日才与上一有效交易日做 diff；
- 同日同摘要：`SAME_TRADE_DATE_NO_CHANGE`，文件和 git 历史均不动；
- 同日摘要发生修正：`SAME_TRADE_DATE_REFRESHED`，更新快照，不产生跨日事件。

定时点由原来的 08:10 北京时间调整为工作日 **08:40**，避免早于上交所盘前 PCF 正式披露窗口。

### 未决问题

- 还没有经历下一真实交易日，因此第一份真实 `events/YYYYMMDD.json` 仍待验证；
- 第一轮跨日事件需要人工复核，看事件类型是否过密、是否存在产品特殊口径；
- 功能分支与 `main` 已明显分叉，待事实层跨日验证后再设计安全整合路径，不直接硬合并。
